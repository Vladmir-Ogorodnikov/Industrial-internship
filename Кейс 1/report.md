# Отчёт: поиск нетипичного поведения заявок на закупку

Выгрузка: 12 162 события, 1 000 заявок (standard 635, contract 197, urgent 168), 1 000 стартов, срез 01.07.2026 00:00 (UTC+3). Итог: **88 строк в `anomalies.csv`, 80 уникальных процессов (8 %), 9 типов отклонений.**

## 1. Инструменты и воспроизводимые шаги

Python 3 + pandas/numpy, один скрипт `analysis.py`. Запуск: `python3 analysis.py students.csv anomalies.csv` — выдаёт файл сдачи и сводку.

1. Чтение CSV (UTF-8 с BOM), перевод `Timestamp` в Europe/Moscow, сортировка внутри процесса по числовому `EventIndex`.
2. Проверка качества: уникальность `EventId`; `EventIndex` идёт 1…n без пропусков в каждом процессе; время не убывает с индексом; `TaskId` создания и закрытия совпадают по процессу и этапу; `ActivityId` ↔ `ActivityName` взаимно однозначны; `RequestType` и `Amount` постоянны внутри процесса; версия шаблона одна. Дефектов структуры нет, полных дублей строк нет.
3. Сборка заданий (created ↔ completed по `TaskId`), длительности: календарная и рабочая (пн–пт 09:00–18:00, без праздников и обеда — как в описании).
4. Кодирование маршрута процесса строкой «этап:результат». Легенда: CHK — Проверка заявки, MGR — Согласование руководителем, BUD — Согласование бюджета, LEG — Проверка договора, EXE — Исполнение, REW — Доработка, AUD — Внеплановая проверка; a = accept, ret = return, rej = reject; END:f / END:r — завершение fulfilled / rejected.
5. Сводные профили (маршруты × тип заявки, роль × этап, длительность по этапу × тип) → критерии → фильтры → текст объяснений с цифрами, подставляемыми из данных.

## 2. Что считаем обычным поведением

- **Маршрут.** 99 % заявок идут по схеме. Основной путь standard/urgent: CHK → MGR → BUD → EXE → завершение (496 + 133 заявки), contract: CHK → MGR → BUD → LEG → EXE (150). Возврат руководителем: MGR:ret → REW → CHK → MGR (119 заявок с одним циклом, у остальных нормальных заявок их нет вообще; 2–4 циклов не встречается). Отказ: MGR:rej → завершение «rejected» (51 заявка). Юрист есть только у contract.
- **Роли.** Роль строго следует этапу: CHK — specialist (6 человек), MGR — manager (6), BUD — finance (6), LEG — legal (6), EXE — procurement (6), REW — requester. Один пользователь = одна роль. Все 1 000 заявок запускает один и тот же заявитель — это особенность выгрузки, не признак.
- **Время.** Все события приходятся на рабочие часы пн–пт; много стартов ровно в 09:00:00 (перенос очереди на начало дня) — артефакт календаря, не аномалия. Медианы рабочих часов на задание (standard / contract / urgent): CHK 0,40 / 0,41 / 0,14; MGR 2,0 / 2,0 / 0,7; BUD 2,6 / 2,5 / 0,9; EXE 4,9 / 5,2 / 1,75; LEG (contract) 3,7; REW 1,4 / 1,4 / 0,45. **Urgent быстрее остальных в 2,5–3 раза на каждом этапе**, поэтому сравнивал каждый этап внутри своего типа заявки. Календарные «выбросы» до 65–95 ч — это выходные: в рабочих часах они укладываются в норму. Паузы между этапами (завершение → создание следующего задания) однородны: медиана ≈ 0,25 раб. ч, максимум 1,8 ч.
- Сумма от типа заявки не зависит, отдельных выбросов по сумме нет.

## 3. Критерии, сравнения, причины выбора

Схема даёт порядок и смысл, а не пороги, поэтому критерии двух видов: **структурные** (маршрут нарушает порядок/состав этапов — однозначно по схеме) и **количественные** (значение далеко от распределения своего этапа и типа заявки, пороги взяты из зазора в данных, а не «на глаз»).

| Тип отклонения | Критерий | Почему так |
|---|---|---|
| Пропущено согласование руководителем | BUD следует сразу за CHK | обязательный этап, остальные 925 заявок без исключений |
| Нарушен порядок: исполнение до бюджета | EXE закрыт раньше создания BUD (и LEG у contract) | порядок задан схемой |
| Повторная проверка без возврата | CHK → CHK без REW между ними | повторная проверка нормальна только после доработки |
| Внеплановая проверка auditor | в маршруте есть AUD | нужен отдельный бизнес-повод; оправданность по редкости не определить |
| Чрезмерные возвраты | ≥ 4 REW в процессе | в норме 0 или 1; значений 2–4 нет, разрыв до 5–8 однозначен |
| Согласование закрыто ролью requester | MGR закрыт пользователем с ролью requester | роль фактического исполнителя не совпадает с этапом (в 2 случаях — самосогласование инициатором 5da4329a) |
| Аномально долгая проверка | раб. длительность CHK ≥ 5 ч | у остальных 1 165 проверок максимум 1,4 раб. ч; аномальные значения — ровно 8 и 60 раб. ч (кластеры) |
| Подозрительно быстрая обработка | ≥ 2 человеческих задания закрыто < 1 мин | остальные заявки ни разу не закрывали задание быстрее 1 мин; здесь 6–19 с на этап |
| Зависшее задание руководителя | MGR открыт на срез и возраст в разы выше нормы | открытость сама по себе не аномалия, но 140–160 дней против максимума 6,8 раб. ч закрытых |

Дополнительно использован робастный z-score (медиана/MAD по логарифму рабочей длительности в разрезе «этап × тип») как «сито» для просмотра хвостов всех этапов: за пределами CHK значимых выбросов нет (максимум z ≈ 3,7 — на границе обычной вариации).

## 4. Результаты

**88 строк, 80 процессов.** По типам: пропущен руководитель — 16; долгая проверка — 16; по 8: исполнение до бюджета, повторная проверка, auditor, чрезмерные возвраты, не-manager закрыл согласование, подозрительно быстрая обработка, зависшее задание руководителя. Пересечение только одно: 8 процессов одновременно пропускают руководителя и имеют проверку ровно 60 раб. ч (две строки у каждого).

Показательные примеры:
- `17b4a994-a650-5539-979c-114b14dc20d6` (urgent) — проверка 60 раб. ч (261 календарный час, 23.04 → 04.05) при медиане 0,14 ч для urgent; затем руководитель пропущен: CHK → BUD → EXE.
- `06dc4973-ce2e-59c5-b252-aa7f1eb62270` — закупщик исполнил заявку 05.03 15:57, бюджет создан лишь в 16:10: CHK → MGR → EXE → BUD.
- `26b4c1f5-fe6b-540d-a343-ae6aac25f87f` — 4 этапа закрыты за 7–19 с каждый, весь процесс 72 мин (норма: проверка ≈ 24 мин, руководитель ≈ 126 мин, бюджет ≈ 170 мин).
- `59ca16a9-80c3-5547-ac6e-babd341ef2b6`, `850a646b-0985-5ed8-9582-3234e9f44d93` — руководителя заменил пользователь с ролью requester, совпадающий с инициатором заявки (самосогласование).
- `42363de6-8f9d-52cc-8601-9de3af18a27c` — 8 возвратов подряд, прежде чем заявка согласована (норма — не более 1).
- `363974d3-8b55-58e7-a74e-7f3b5ec0a6b7` — задание руководителя висит с 26.01, 156 дней на срез.

## 5. Ложные срабатывания, ограничения, ручная проверка

- **Не помечены намеренно:** 2 открытых задания EXE (`70cfce39…`, `f273e429…`) — возраст 6–10 календарных часов на срез, обычное ожидание. Заявки с календарной длительностью 60–95 ч, где рабочая — норма (выходные). Единичные urgent-значения чуть выше хвоста (BUD 3,06 и MGR 2,45 раб. ч) — граница нормальной вариации, не дефект. Крупные суммы без отклонений по маршруту.
- **Требуют ручной проверки:** (а) 8 заявок с auditor — это может быть законная внеплановая проверка, по данным повод не виден; (б) 8 «слишком быстрых» — возможна автоматизация/тестовые данные, а не нарушение; (в) 8 закрытий согласования ролью requester — возможно делегирование/замещение руководителя; в 2 случаях самосогласование, одно решение — отказ (`65ba6ad5…`); (г) 8 процессов с 5–8 возвратами — может быть реальный сложный случай; (д) 8 зависших MGR — потерянное задание или неактуальная заявка.
- **Ограничения метода:** пороги выведены из этих же данных (в них чистые зазоры, поэтому результат устойчив, но на «грязных» данных потребуется настройка); праздники, обед и отпуска не учитываются; длительность задания включает ожидание, а не чистую работу; один инициатор и по 6 пользователей на роль не позволяют искать аномалии «по пользователю»; причины отклонений по данным неизвестны — результат это кандидаты, а не доказанные нарушения. Возможны аномалии, не выражающиеся ни в маршруте, ни в длительности (например, по содержанию заявки) — в журнале их увидеть нельзя.
